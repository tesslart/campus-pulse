# Подготовка к защите

## Вопросы преподавателя — короткие ответы

**Где хранятся данные?**
В облачной PostgreSQL проекта Supabase: таблицы `public.events` и `public.event_members`. Пользователи — в `auth.users` (Supabase Auth). В браузере данные не хранятся: localStorage содержит только сессию входа, которую создаёт supabase-js.

**Почему publishable key можно использовать в браузере, а secret — нельзя?**
Publishable (anon) key лишь идентифицирует проект; запросы с ним выполняются от ролей `anon`/`authenticated` и ограничены GRANT и RLS. Secret / service_role key обходит RLS и даёт полный доступ к базе — попав в JS-сборку или GitHub, он позволит кому угодно читать и удалять все данные.

**Что произойдёт без RLS?**
Код в браузере открыт, любой может отправить запрос в API напрямую (из консоли). Без RLS пользователь Б смог бы изменить или удалить событие А, прочитать списки участников и записать другого человека. Проверки в интерфейсе (скрытые кнопки) не защищают.

**Чем отличаются commit, branch и pull request?**
Commit — снимок изменений с сообщением. Branch — отдельная линия коммитов для задачи (`feature/*`), не трогающая `main`. Pull request — запрос на слияние ветки в `main` с обсуждением, review и проверкой CI.

**Как вы проверили, что Б не может редактировать событие А?**
1. В UI: у Б нет кнопок, `#/edit/<id>` показывает «Нет доступа».
2. В БД: `supabase/rls_tests.sql` — UPDATE/DELETE от Б затрагивают 0 строк, смена `creator_id` → `permission denied`.
3. Через API: `npm run test:rls` от имени реального аккаунта Б.

## Две ступени защиты в нашей схеме

1. **GRANT** — роли `authenticated` разрешены INSERT/UPDATE только колонок `title, description, category, starts_at, location, cover_style`. `creator_id` заполняет БД (`default auth.uid()`), подменить его невозможно.
2. **RLS** — политики `creator_id = auth.uid()` для UPDATE/DELETE событий и `user_id = auth.uid()` для чтения/записи/удаления участия.

## Фото и видео (PRO-функция)

- **Где хранятся фото?** В Supabase Storage, bucket `event-media`. В таблице `events.photos` — только пути к файлам; первое фото — обложка.
- **Кто может загружать?** Политики на `storage.objects`: загрузка и удаление только в папку `<свой user_id>/`. Bucket ограничен 5 МБ и типами JPG/PNG/WEBP/GIF.
- **Почему видео — ссылкой?** Видео весят сотни мегабайт; бесплатный Storage маленький. Ссылка проверяется в браузере (`parseVideoUrl`) и в БД (CHECK `^https://`). В iframe подставляется адрес, собранный из ID видео, а не то, что ввёл пользователь, — так нельзя встроить чужой сайт.
- **Сжатие:** перед загрузкой фото уменьшается до 1600 px и конвертируется в WEBP (canvas), обычно 100–400 КБ вместо нескольких МБ.

## Сценарий демонстрации (5 минут)

1. Открыть ссылку GitHub Pages на телефоне — афиша загружается.
2. Ноутбук, окно 1: вход А → создать событие.
3. Окно 2 (инкогнито): вход Б → обновить → событие есть → «Участвовать» → «Вы участвуете».
4. Б: нет кнопок редактирования; показать вывод `npm run test:rls`.
5. Показать Supabase Table Editor: строки и пометку RLS enabled.
6. Показать GitHub: Issues, 2 PR, комментарий review, вкладку Actions.
